# MASTER AUDIT REPORT

**Date:** May 12, 2026
**Target:** Symeno Storefront & Auth Architecture
**Status:** CRITICAL VULNERABILITIES IDENTIFIED

---

### 1. The Redirection Chain (The Loop of Death)
*   **Files Involved:** `src/middleware.ts`, `src/pages/checkout/index.astro`
*   **Mechanism of Failure:** `src/pages/checkout/index.astro` correctly detects an unauthenticated user (`Astro.locals.user` is undefined) and redirects them to `/auth/login?returnTo=/checkout`. After a successful login/registration, the client redirects back to `/checkout`. However, in `src/middleware.ts`, the route guard only decrypts the JWT and populates `Astro.locals.user` for `isAdminRoute`, `isAccountRoute`, and `isSecureApiRoute`. It completely bypasses `/checkout`.
*   **Why it is failing:** Because the middleware ignores the `/checkout` route, `Astro.locals.user` remains `undefined` when the server renders the page. This causes `checkout/index.astro` to immediately bounce the newly authenticated user back to the login page, creating an inescapable infinite redirect loop.
*   **Strategy to Patch:** In `src/middleware.ts`, define `const isCheckoutRoute = url.pathname.startsWith('/checkout') || url.pathname.startsWith('/api/checkout');` and include it in the `if` block that validates the session token.

### 2. Frontend Event Hijacking
*   **Files Involved:** `src/pages/auth/login.astro`, `src/pages/auth/register.astro`
*   **Mechanism of Failure:** Both login and registration forms use `<form method="POST">` and rely on a client-side JavaScript script (`e.preventDefault()`) to intercept the submission. However, this logic is wrapped inside an `astro:page-load` event listener for Astro View Transitions. 
*   **Why it is failing:** If a user submits the form quickly before Astro's View Transitions fully hydrate the script, or if a third-party component (like Turnstile) delays execution, the browser executes a native `POST` request to the current URL. Because `.astro` files lack a server-side `export const POST` handler, Astro simply re-renders the page. This manifests as a silent page refresh, dropping all form state without throwing an error.
*   **Strategy to Patch:** Remove `method="POST"` from both `<form>` elements and add an inline `onsubmit="event.preventDefault();"` attribute. This guarantees the browser cannot execute a native POST bypass, forcing it to wait for the Astro-hydrated script.

### 3. Database & API Synchronization
*   **Files Involved:** `src/pages/api/auth/register.ts`, `src/pages/api/auth/login.ts`, `migrations/schema.sql`
*   **Mechanism of Failure:** 
    1.  **Dropped Cart Payload:** `register.ts` accepts `cartItems: z.array(z.any())` from the frontend's Svelte store but does absolutely nothing with it. The pre-registration cart state is wiped out upon account creation.
    2.  **Turnstile Security Bypass:** Both `register.ts` and `login.ts` schemas accept `'cf-turnstile-response'`, but neither API actually sends this token to Cloudflare's `/siteverify` endpoint. Bot protection is currently dead logic.
    3.  **Fatal Hash Destructuring:** In `login.ts`, the code executes `const [saltHex] = (user.password_hash as string).split(':');`. If a legacy user or manually inserted database record has a password hash without a `:` delimiter, this destructuring fails and crashes the API with an unhandled 500 error.
*   **Why it is failing:** The data payloads between the frontend and backend are desynchronized, security validations are mocked but not enforced, and D1 queries lack defensive edge-case handling.
*   **Strategy to Patch:** Implement a `fetch` call to Cloudflare's `siteverify` endpoint in both auth APIs. In `register.ts`, process the `cartItems` array by syncing it to a dedicated `carts` table in D1. Add a `.includes(':')` check in `login.ts` before attempting to destructure the hash.

### 4. Session Hydration & Middleware
*   **Files Involved:** `src/lib/auth.ts`, `src/middleware.ts`
*   **Mechanism of Failure:** There is NO KV session creation happening in the Auth APIs. The architecture is entirely stateless, utilizing JWTs generated by `createSession` in `auth.ts`. The only KV interaction is a revocation check (`kvStore.get('revoked:...')`) in `middleware.ts`. Furthermore, `createSession` forcefully sets the `auth_session` cookie with `secure: true`.
*   **Why it is failing:** If local development runs on `http://localhost` without HTTPS, the browser will silently refuse to set the `secure: true` cookie. This completely breaks the auth pipeline locally while appearing perfectly fine in the code. Additionally, the architectural mental model is misaligned: the system is stateless JWT, not stateful KV.
*   **Strategy to Patch:** Dynamically set the `secure` cookie flag based on the environment (`process.env.NODE_ENV === 'production'`). Update architectural documentation to reflect that sessions are JWT-based, removing KV terminology unless explicitly building a stateful store.

### 5. Missing Infrastructure
*   **Files Involved:** `src/pages/api/checkout/process.ts`
*   **Mechanism of Failure:** `process.ts` relies on an `EMAIL_QUEUE` binding (`const queue = (env as any).EMAIL_QUEUE;`) to process async order confirmations via a Cloudflare Queue.
*   **Why it is failing:** The Mailroom worker (the queue consumer) that is supposed to process `EMAIL_QUEUE` messages is absent from the immediate Astro project structure. If the binding exists but the consumer is not deployed, the queue will dead-letter or back up silently, and customers will never receive order confirmations.
*   **Strategy to Patch:** Verify the existence of the external Cloudflare Worker consumer for `EMAIL_QUEUE`. If it does not exist, build the consumer worker or route the emails synchronously via an external API (e.g., Resend, AWS SES) directly within `process.ts`.
